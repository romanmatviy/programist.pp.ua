        <h2>Вступ: Від моноліту до розподілених систем</h2>
        <p>На початку розвитку будь-якого проекту найпростішим і найефективнішим рішенням є розробка **монолітного додатку**. У моноліті весь код (користувачі, платежі, товари, логістика) знаходиться в одній кодовій базі та використовує спільну базу даних. Це значно прискорює розробку на початкових етапах.</p>
        <p>Проте, коли проект масштабується, над ним починають працювати десятки розробників, а навантаження на певні модулі зростає, моноліт перетворюється на перешкоду. Одне невдале оновлення модуля доставки може повністю зупинити процес прийому платежів. Саме тут на допомогу приходить <strong>мікросервісна архітектура</strong>.</p>
        
        <h2>1. Ключові принципи мікросервісів</h2>
        <p>Мікросервісна архітектура передбачає поділ єдиного великого додатку на набір невеликих, незалежних сервісів, кожен з яких відповідає за окрему бізнес-функцію.</p>
        <ul>
          <li><strong>База даних для кожного сервісу (Database-per-service):</strong> Сервіси ніколи не повинні звертатися безпосередньо до бази даних один одного. Обмін даними відбувається виключно через чітко задеклароване API. Це усуває жорстку залежність на рівні таблиць.</li>
          <li><strong>Незалежне розгортання:</strong> Ви можете оновити код сервісу рекомендацій без необхідності перезапускати або перезбирати сервіс кошика покупок.</li>
          <li><strong>Event-Driven комунікація:</strong> Для асинхронного зв'язку між сервісами використовуються брокери повідомлень типу RabbitMQ або Apache Kafka. Це запобігає падінню системи, якщо якийсь із сервісів тимчасово недоступний.</li>
        </ul>

        <h2>2. Паттерн API Gateway: Єдина точка входу</h2>
        <p>Для того, щоб клієнтська частина додатку (фронтенд чи мобільний додаток) не взаємодіяла безпосередньо з десятками мікросервісів, використовують паттерн **API Gateway** (наприклад, Kong, Ocelot чи Nginx). Він приймає всі запити від клієнтів, здійснює маршрутизацію до відповідного мікросервісу, а також бере на себе завдання авторизації та лімітування запитів (rate limiting):</p>
        <pre><code class="language-nginx"># Приклад конфігурації Nginx як API Gateway
server {
    listen 80;
    server_name api.programist.pp.ua;

    location /api/v1/users {
        proxy_pass http://users_service:3001;
    }

    location /api/v1/payments {
        proxy_pass http://payments_service:3002;
    }

    location /api/v1/products {
        proxy_pass http://products_service:3003;
    }
}</code></pre>

        <h2>Висновок</h2>
        <p>Перехід на мікросервісну архітектуру — це складне управлінське та технічне рішення. Воно вимагає високої кваліфікації команди в області DevOps, оркестрації контейнерів (Kubernetes) та моніторингу систем. Не починайте новий стартап із мікросервісів — почніть із модульного моноліту та відокремлюйте сервіси лише тоді, коли в цьому дійсно виникне технічна потреба.</p>
